# Blog post

## Reader

The audience the briefing names. If the briefing names none, write for a general user of the product and ask one question at the end of the turn: "Who is this for?" Whoever it is, they skim and want to know what is different for them.

## Parts

Write these parts in this order, one line each unless noted.

1. Title. Plain, states the change, no hype.
2. Story. One or two lines on the problem a user had before this change.
3. Change. Two or three lines on what is new and what the user can now do.
4. Proof. One line with a number or an example, labelled with where it comes from, such as "measured in the beta" or "from the release notes". If no source has one, write "none in the sources".
5. Caveat. One line on what the change does not do yet, or a limit the user should know. If no source names one, write "none in the sources".
6. Status and next step. One line that says whether it is released, in beta or planned, and what the reader can do next. If no source says which, leave the status out and ask "Is it out yet?" at the end of the turn.

Put a source marker such as [1] after every claim in parts 2 to 6. The title carries no marker. A "none in the sources" line carries no marker.

## Length

7 to 12 lines in total. 60 to 250 words in total. The title counts as a line. Markers, the Sources list and the Not traced list are not counted. When a part says "none in the sources", the minimum word count does not apply. Cut a part before you pad one.

## Sources

Mark each claim in the text with [1], [2] and so on. After the post, add a "Sources" list with one entry per marker. Each entry is the link the user gave, or "pasted text: <first five words>" when the user pasted it in. Every link the user gave appears in the list, or appears as "not used, because <reason>". Claims you could not trace to any source go under a "Not traced" heading after the list, one per line, and stay out of the post text.
