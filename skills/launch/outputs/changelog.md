# Changelog entry

## Reader

The audience the briefing names. If the briefing names none, write for a general user of the product and ask one question at the end of the turn: "Who is this for?" Whoever it is, they skim a list of changes and stop only when something affects them.

## Parts

Write these parts in this order, one line each unless noted.

1. Heading. The name of the change in a few words.
2. Status tag. Exactly one of beta, planned or released. Take it from what a source says about availability, such as "available now", "in beta" or "coming in March", and not from whether a date exists. A past or current release date does not make it released unless a source says it is out, and a future date does not make it planned unless a source says it is not out yet. If no source says, ask "Is it out yet?" at the end of the turn, use planned in the draft and list the question under "Not traced". A missing date is a separate question under "Not traced".
3. Summary. One line on what changed for the user.
4. Changes. Up to three short lines, each one visible change.

Put a source marker such as [1] after every claim in parts 2 to 4. The heading carries no marker.

## Length

4 to 6 lines in total. 8 to 60 words in total. Each change line is one sentence. Markers, the Sources list and the Not traced list are not counted.

## Sources

Mark each claim in the text with [1], [2] and so on. After the entry, add a "Sources" list with one entry per marker. Each entry is the link the user gave, or "pasted text: <first five words>" when the user pasted it in. Every link the user gave appears in the list, or appears as "not used, because <reason>". Claims you could not trace to any source go under a "Not traced" heading after the list, and stay out of the entry text.
