# Feature article recipe

Version 1.0.0. Original Launch Factory instructions for the `blog_editor` draft or revision stage. Enter through the launch-factory operator and the existing specialist request and route contracts.

## Inputs

Use the original `specialist-request/v1` packet and validated route projection. Resolve selected inputs against `workspace_root`; inspect the shared protocol, blog reference bank and the chosen voice file. The operator also supplies:

- The intended reader, publisher and one action the article should help the reader take.
- The current feature or product scope, including availability and an approved claim ledger with required qualifiers. When the human authorizes drafting before a separate Claims Lock decision, retain that decision as pending and cite the scoped drafting instruction.
- A concrete source-supported use case, or an explicitly illustrative scenario chosen by the human.
- Current channel examples or an original voice guide with source receipts. These govern expression and article structure only.
- Approved media references with exact versions and hashes, plus permission to derive still frames when applicable.
- The selected CTA text and destination, supplied metadata requirements, and any prior artifact-specific feedback.

If evidence is missing, omit the unsupported statement or record the precise gap in the review sidecar. A draft should still be completed wherever the authorized scope permits. Do not invent a result to fill an outline.

## Write the article

Establish the reader's job and choose a useful order for explaining it. Read actual channel articles before adopting their voice. Derive the structure from the relevant sample: a feature introduction usually needs a concrete opening, a demonstrated workflow, useful details and an exact next action. Article length follows the supported material and the reader's needs.

Outline the sections before writing. Draft the whole article, then revise the opening and remove repeated explanations. Use one coherent example across the body when it helps the reader follow the decision. Keep hypothetical details visibly hypothetical. A scenario price belongs to that scenario, never to product pricing or a platform limit.

Map product statements to eligible claim IDs and preserve each qualifier. Availability must follow current source evidence. Explain a preview boundary in one natural paragraph close to the first capability description. Put roadmap content under an explicit future heading and retain prerequisites where they affect the claim. Never turn a rendered product scene into proof of a live integration or purchase.

Keep the selected publisher's identity intact when adapting another company's channel style. Do not import the example author's identity, first-person experiences, metrics, commercial terms or product claims. Write original prose and respect the human's prose constraints over generic templates or analyzer advice.

Place permitted images beside the relevant explanation. Supply meaningful alt text, an appropriate caption and the local asset path. Record the exact parent media hash and extraction frame for any derived still. Preserve the original image composition unless an image edit is separately in scope. A new image placement remains part of the article's human review.

## Return the full draft

Return `article.md` with a title, dek and clean Markdown body. Keep claim identifiers and operational notes in companions. Return `metadata.json` containing the slug, SEO title, description, proposed byline, category, CTA and image fields. Publication fields remain unset until a real publication decision.

Return a provenance sidecar that binds the artifact version and SHA-256 to the product, source revision, request, route and selected voice. Map every paragraph or other prose block by exact text/hash and line location to claim IDs, scenario evidence, editorial reasoning or asset evidence. Include headings, image captions and metadata assertions in the review scope. Record human review as pending; do not infer approval from route success.

Return image provenance and a short review note listing checks performed, meaningful limitations and the precise artifact the human is being asked to review. If a writing skill or analyzer ran, record its real entrypoint and result. A file read, script execution and native specialist invocation are distinct evidence states.

## Check before review

Verify selected source file hashes and exact Unicode claim spans. Confirm all cited claims belong to the selected product and all draft references resolve. Read the complete article for semantic support, including image text and CTA implications; a hash check cannot prove that a sentence follows from its source.

Inspect the final images and check title/description length, paragraph flow, repetition, spelling and the user's prose constraints. Use SEO and voice tools as diagnostics when available. Do not add filler, repeat keywords or fabricate internal links to satisfy a score. Report checks that did not run as `not_tested`.

For a revision, carry forward the named feedback and update only the article and its direct dependencies. Recompute hashes for changed bytes and return the exact revised package to the human. This recipe performs no publishing, paid generation or approval event writes. The operator owns the next authorized action.
