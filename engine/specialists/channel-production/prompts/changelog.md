# Source-bound changelog entry

Inputs: validated `specialist-request/v1` for `changelog`, selected changelog expression profile, claim ledger with rollout qualifiers, release status, and approved destination. Read the changelog reference bank. Style sources are not product evidence.

Write the headline around the supported change. Open with the concrete behavior and the reader's task. For one feature, prefer a short explanation followed by useful actions or a compact scenario. A release roundup can group changes by category. Match the selected source's format without copying its wording, company identity or claims.

State preview or planned status when the evidence requires it. Do not use “now live,” “available to everyone,” exact plan access or navigation paths without proof. If no production release is established, write a preview update and put the missing release/access check in metadata. Keep the user-facing explanation helpful and concise.

Return a clean Markdown entry, matching HTML preview, title/category/status/CTA metadata and a paragraph-level claim map. The CTA must match the current product brief. Add a relevant product image when supplied; do not use decorative screenshots that imply completed purchases or integrations.

The channel editor checks change clarity and availability wording. The quality reviewer checks the exact artifact against selected claims. Save the version, hash and dependencies for the human review. A changed source or body invalidates the old review binding. Revise only the affected entry, with at most two editorial retries before a named human issue. This prompt never publishes a changelog.
